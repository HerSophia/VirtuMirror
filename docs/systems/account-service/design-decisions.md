# 设计决策

本文档记录账号系统服务设计过程中的关键决策及其理由。

---

## 决策 1：双层作用域模型

### 问题

如何让玩家在不同"世界"（角色卡）中拥有不同的社交身份，同时保持"玩家是同一个人"的一致性？

### 方案对比

| 方案 | 描述 | 优点 | 缺点 |
| ---- | ---- | ---- | ---- |
| **A: 单层作用域** | 实体和账号共用同一个作用域 | 简单 | 无法实现"全局玩家 + 世界专属账号" |
| **B: 账号继承实体** | 账号强制继承实体的作用域 | 较简单 | 同上 |
| **C: 双层独立作用域** | 实体和账号各自有独立作用域 | 灵活 | 需要约束规则 |

### 决策

选择 **方案 C：双层独立作用域**

### 理由

1. **核心场景需求**：玩家（全局实体）需要在不同世界有不同的社交账号
   ```text
   玩家实体 (global)
       ├── 微博 @都市小王 (character: 霸道总裁)
       ├── 微博 @剑仙无名 (character: 剑仙传)
       └── 微博 @测试号 (global)
   ```

2. **约束规则简单**：账号作用域不能比实体"更全局"

3. **向后兼容**：简单场景（实体和账号同作用域）仍然支持

## 决策 2：关系绑定在账号而非实体

### 问题

社交关系（关注、好友）应该建立在哪个层级？

### 方案对比

| 方案 | 描述 | 优点 | 缺点 |
| ---- | ---- | ---- | ---- |
| **A: 实体间关系** | 关系建立在 CharacterEntity 之间 | 简单，跨平台统一 | 无法区分不同世界的社交圈 |
| **B: 账号间关系** | 关系建立在 PlatformAccount 之间 | 支持世界隔离 | 稍复杂 |

### 决策

选择 **方案 B：账号间关系**

### 理由

1. **世界隔离需求**：同一个玩家在不同世界应该有不同的社交圈
   ```text
   在"霸道总裁"世界：
     玩家的微博粉丝 → 白领群体
   
   在"剑仙传"世界：
     玩家的微博粉丝 → 修仙者群体
   ```

2. **平台差异性**：不同平台的关系语义不同（微博关注 vs 微信好友）

3. **数据一致性**：账号删除时可以简单地级联删除关系

## 决策 3：玩家实体全局唯一

### 问题

玩家实体应该是每个世界一个，还是全局唯一？

### 方案对比

| 方案 | 描述 | 优点 | 缺点 |
| ---- | ---- | ---- | ---- |
| **A: 每世界一个** | 每个角色卡有独立的玩家实体 | 完全隔离 | 丢失"玩家是同一个人"的语义 |
| **B: 全局唯一** | 系统中只有一个玩家实体 | 一致性好 | 需要账号级隔离 |

### 决策

选择 **方案 B：全局唯一**

### 理由

1. **语义正确**：玩家作为"真人"跨越所有虚拟世界

2. **双层作用域解决隔离**：通过账号级作用域实现世界隔离

3. **便于管理**：账号管理 App 可以展示"我在各个世界的身份"

## 决策 4：User Pool 只生成不存储

### 问题

随机用户生成器（User Pool）的职责边界是什么？

### 方案对比

| 方案 | 描述 | 优点 | 缺点 |
| ---- | ---- | ---- | ---- |
| **A: 生成+存储** | User Pool 维护自己的用户池 | 原有设计 | 数据孤岛，与账号系统割裂 |
| **B: 只生成** | User Pool 只生成数据，存储交给 AccountService | 职责清晰 | 需要重构 |

### 决策

选择 **方案 B：只生成**

### 理由

1. **消除数据孤岛**：所有用户数据统一存储在 AccountService

2. **统一查询**：`getVisibleAccounts` 可以返回所有来源的用户

3. **作用域支持**：生成的用户自动获得正确的作用域

---

## 决策 5：作用域自动推断

### 问题

创建实体/账号时，是否要求显式指定作用域？

### 方案对比

| 方案 | 描述 | 优点 | 缺点 |
| ---- | ---- | ---- | ---- |
| **A: 必须显式指定** | 创建时必须传入 scope | 明确，不会出错 | 繁琐，调用方需要理解作用域 |
| **B: 自动推断** | 根据上下文和类型自动设置 | 简洁 | 可能不符合预期 |
| **C: 可选指定** | 不指定时自动推断，指定时使用指定值 | 灵活 | 需要文档说明规则 |

### 决策

选择 **方案 C：可选指定**

### 理由

1. **简化常见场景**：大多数情况下自动推断即可
   - NPC → session
   - 角色卡导入 → character
   - 玩家 → global（强制）

2. **保留灵活性**：特殊场景可以显式指定

3. **安全兜底**：玩家实体强制全局，防止误用

## 决策 6：微博保持现有实现

### 问题

微博 App 已有的会话管理实现是否需要迁移到系统服务？

### 方案对比

| 方案 | 描述 | 优点 | 缺点 |
| ---- | ---- | ---- | ---- |
| **A: 完全迁移** | 微博改用 SessionContextService | 统一 | 迁移风险，工作量大 |
| **B: 保持现状** | 微博内部实现不变，只对接 AccountService | 风险低 | 两套实现 |
| **C: 渐进迁移** | 新功能用系统服务，旧功能逐步迁移 | 平衡 | 过渡期复杂 |

### 决策

选择 **方案 B + 可选 C**

### 理由

1. **微博已稳定运行**：不值得为统一而引入风险

2. **AccountService 集成已完成**：用户数据来源已统一

3. **新 App 使用系统服务**：抖音、B站等新 App 直接用

4. **未来可选迁移**：如果需要，微博可以逐步迁移

## 决策 7：账号创建弹窗组件化

### 问题

各平台 App 都需要"创建账号"功能，如何避免重复实现？

### 方案对比

| 方案 | 描述 | 优点 | 缺点 |
| ---- | ---- | ---- | ---- |
| **A: 各自实现** | 每个 App 实现自己的创建弹窗 | 完全定制 | 重复代码，风格不统一 |
| **B: 公共组件** | 抽取通用的 CreateAccountDialog | 复用，统一 | 需要支持定制 |

### 决策

选择 **方案 B：公共组件**

### 理由

1. **大部分逻辑相同**：用户画像、随机生成、作用域选择

2. **支持定制**：通过 props 支持主题色、平台名等定制

3. **用户体验一致**：跨平台统一的账号创建体验

### 组件设计

```vue
<CreateAccountDialog
  :visible="showDialog"
  platform-id="weibo"
  platform-name="微博"
  :theme-color="'#E6162D'"
  :show-scope-selector="false"
  @close="showDialog = false"
  @created="handleCreated"
/>
```

## 决策 8：级联删除策略

### 问题

删除实体或账号时，关联数据如何处理？

### 方案对比

| 方案 | 描述 | 优点 | 缺点 |
| ---- | ---- | ---- | ---- |
| **A: 禁止删除** | 有关联数据时禁止删除 | 安全 | 不灵活 |
| **B: 级联删除** | 自动删除关联数据 | 简洁 | 可能误删 |
| **C: 软删除** | 标记删除，不真正删除 | 可恢复 | 复杂 |

### 决策

选择 **方案 B：级联删除**

### 理由

1. **数据一致性**：孤儿数据（无实体的账号）无意义

2. **简化实现**：不需要处理孤儿数据

3. **可预期**：删除操作的结果明确

### 级联规则

```text
删除 CharacterEntity
    ├── 删除所有 PlatformAccount (entityId = entityId)
    └── 删除所有 SocialRelation (涉及被删账号)

删除 PlatformAccount
    └── 删除所有 SocialRelation (涉及该账号)
```

## 决策 9：Handle 唯一性范围

### 问题

平台账号的 handle（@用户名）在什么范围内需要唯一？

### 方案对比

| 方案 | 描述 | 优点 | 缺点 |
| ---- | ---- | ---- | ---- |
| **A: 全局唯一** | 同平台所有 handle 唯一 | 简单 | 不同世界可能冲突 |
| **B: 作用域内唯一** | 同平台同作用域内唯一 | 灵活 | 复杂 |
| **C: 不强制唯一** | 允许重复 | 最灵活 | 可能混淆 |

### 决策

选择 **方案 B：作用域内唯一**（当前实现为 A，计划改进）

### 理由

1. **现实逻辑**：不同"世界"是独立的，用户名可以相同

2. **避免冲突**：不同角色卡的 NPC 可能有相同名字

3. **查询优化**：配合作用域查询，不会查到重复

### 实现

```typescript
// 检查唯一性时考虑作用域
async function isHandleAvailable(
  platformId: string,
  handle: string,
  scope: AccountScope,
  scopeId?: string
): Promise<boolean> {
  const existing = await db.platformAccounts
    .where('[platformId+handle]')
    .equals([platformId, handle])
    .filter(acc => {
      // 同作用域才算冲突
      if (acc.scope !== scope) return false;
      if (scope === 'session') return acc.scopeSessionId === scopeId;
      if (scope === 'character') return acc.scopeCharacterCardId === scopeId;
      return true; // global
    })
    .first();
    
  return !existing;
}
```

## 决策总结

| 决策 | 选择 | 核心理由 |
| ---- | ---- | -------- |
| 作用域模型 | 双层独立 | 支持"全局玩家 + 世界专属账号" |
| 关系绑定 | 账号级 | 支持不同世界的社交圈隔离 |
| 玩家实体 | 全局唯一 | 语义正确，便于管理 |
| User Pool | 只生成不存储 | 消除数据孤岛 |
| 作用域指定 | 可选+自动推断 | 简化常见场景，保留灵活性 |
| 微博迁移 | 保持现状 | 降低风险 |
| 账号创建 | 公共组件 | 复用代码，统一体验 |
| 删除策略 | 级联删除 | 数据一致性 |
| Handle 唯一 | 作用域内唯一 | 避免跨世界冲突 |
